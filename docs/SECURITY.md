# Security Policy

The n3n project considers bugs to be bugs.  The standpoint is that there is
generally no difference between a bug and any subset of bugs that have been
considered as special.

- There is no bug bounty.
- There is no special security advisory process.
- There are no arrangements with any users of n3n packages for whom advance
  notification could be provided.
- There is no security mailing list.
- There is no special recognition for finders of security bugs.  Patches
  proposed and merged will have the usual git attributions.

Each bug will be considered on a case-by-case basis and may be triaged
differently - if you find a bug which you consider should be treated in a
specific way, please feel free to make contact and discuss.

Since there is no downstream communication other than the publishing of new
releases and packages, the embargo period that is often suggested with bug
reports often does provide much value and simply patching the bug and making a
new release is probably the best way forward.

Remember to ensure in all communications that your information is succinct,
too the point and easy to digest.  While large information dumps may be useful
for repeatability, history and deep diving into the issues, this should be
considered as one or more appendixes to the bug report.  The main bug report
should be two or three paragraphs the clearly describe the details needed for
a human to quickly triage the bug.  (This should be the same for raising any
bug)

The normal bug process seen in the [Contributing](Contributing.md) docs is
expected to be used - even if the bug is kept private and/or github tickets
are not used for managing the bug.
